# クアトロマップ大阪 検索成長施策デザイン

## 目的

「クアトロフォルマッジ 大阪」「大阪 クアトロフォルマッジ」を主要検索語とし、大阪で実際に店を選びたい利用者にとって最も確認しやすく、信頼できる専門サイトを目指す。順位は保証対象にせず、公開可用性、検索エンジンによる理解、独自価値、利用者満足度、計測可能性を改善する。

## 採用方針

採用案は「公開復旧＋コンテンツ品質＋技術SEOの一体改善」。公開情報で初期品質を引き上げ、管理人による実食レビューと独自写真を順次追加する。検索流入だけを目的とする薄い地域ページの大量生成、キーワード詰め込み、未体験の実食情報、根拠のないおすすめ順位は作らない。

## 現状認識

- GitHub Pagesの公開URLは検索結果に一度登録されているが、2026-08-01の外部確認では404を返した。最初の優先事項は公開復旧である。
- サイトにはトップ、54件の公開店舗、11区ページ、目的別・駅別ガイド、店舗詳細、robots.txt、sitemap.xml、canonical、Search Console所有権確認、JSON-LDがある。
- 店舗データには確認日と情報源がある一方、実食レビューはまだ十分ではない。
- 店舗ページの`aggregateRating`はGoogle Maps上の評価を表している。自サイトで収集した評価と誤認されないよう、リッチリザルト用の集計評価としては出力しない。
- コピー先には正常なGit履歴がないため、実装前にGitHub上の正本を取得して作業履歴を正常化する。

## 情報設計

### 1. トップページ

主要検索語に対する中心ページとする。タイトル、H1、冒頭説明は自然な日本語で「大阪でクアトロフォルマッジを探す」という目的を明示する。店舗件数、最終更新日、掲載基準、確認済み件数を表示し、区・駅・目的別ガイドへのクロール可能なリンクを配置する。

### 2. 店舗詳細ページ

店舗選びの意思決定に必要な情報を一か所にまとめる。

- 店名、区、最寄り駅、住所、地図
- クアトロフォルマッジの提供確認状態、確認日、確認元
- 価格、チーズ構成、はちみつ、ランチ、テイクアウト
- 営業情報は変更可能であることと公式確認先
- Google Maps評価は出典付きの参考情報として画面に表示するが、自サイト評価として構造化しない
- 実食済みの場合のみ訪問日、独自コメント、独自写真を掲載する

### 3. 区・駅・目的別ページ

検索語の違いではなく、利用者の選択行動に役立つ分類として維持する。各ページに、その地域・目的固有の導入文、掲載件数、確認済み件数、選び方、店舗一覧を持たせる。該当店舗が少ない、または独自説明を用意できない分類はindex対象として増やさない。

### 4. 信頼性ページ

以下を独立ページまたは明確なセクションとして提供する。

- 運営者情報
- サイトを作った目的
- 店舗の選定・確認方法
- 「確認済み」の定義
- Google Maps等の外部情報の扱い
- 更新・訂正方針
- AIや自動処理を利用した箇所がある場合の説明

## 技術SEO

- GitHub Pagesのデプロイを復旧し、全主要URL、CSS、JavaScript、画像、robots.txt、sitemap.xmlが200を返すことを確認する。
- 各ページに固有で説明的なtitle、meta description、canonical、OG情報を設定する。
- トップ、区、ガイド、店舗の全index対象ページを通常の`<a>`リンクで相互接続する。
- sitemapの`lastModified`は実際のページまたは店舗データ更新日から生成する。根拠のない一律更新日は使わない。
- 構造化データは画面上で確認できる情報だけをJSON-LDで出力する。
- 店舗には`Restaurant`、階層には`BreadcrumbList`、一覧には`ItemList`を使う。
- 自サイトで収集していないGoogle評価を`aggregateRating`として出力しない。
- Search Consoleの所有権確認を維持し、サイトマップを登録する。
- 静的出力を維持し、モバイル表示、アクセシビリティ、表示速度を壊さない。

## コンテンツ運用

初期リリースでは既存の公開情報を、出典、確認日、確認状態とともに整理する。以後は実食した店舗から順に、訪問日、味の特徴、はちみつとの相性、価格感、独自写真を追加する。未訪問店舗に実食したような表現は使用しない。

店舗更新時は次を確認する。

1. 公式メニューまたは店舗公式情報
2. Google Maps上の所在地と営業情報
3. クアトロフォルマッジの提供状況
4. 確認日と出典URL
5. サイト上の表示と構造化データの一致

## 計測

主要KPIはSearch Consoleで計測する。

- 主要2検索語の表示回数、クリック数、CTR、平均掲載順位
- 区・駅・目的別検索語の表示回数とクリック数
- index登録された有効ページ数
- クロール、canonical、構造化データのエラー数

GA4が設定できる場合は、店舗詳細閲覧、地図クリック、公式サイトクリック、検索・絞り込み利用を補助指標にする。施策前の値を基準値として保存し、公開後28日単位で比較する。

## エラー処理と安全性

- デプロイ失敗時は旧公開物を破壊せず、GitHub Actionsログから原因を特定する。
- 必須情報が欠ける店舗のJSON-LDには不完全なプロパティを出力しない。
- 外部URLや画像が無効な場合でもページ全体は表示できるようにする。
- Search ConsoleやGitHubへの書き込み操作は対象を明示して実施する。
- 順位保証、被リンク購入、クローキング、隠しテキスト、重複ページ量産は行わない。

## テスト戦略

- SEOユーティリティの単体テスト：URL、canonical、title、description、JSON-LD生成
- sitemapテスト：index対象URLの網羅、重複排除、実更新日の反映
- 構造化データテスト：必須項目、画面表示との一致、外部評価の非出力
- ページテスト：トップ、区、ガイド、代表店舗の見出しと内部リンク
- 既存テスト、ESLint、TypeScript、Next.js本番build
- 静的出力のリンク・画像・robots・sitemapのHTTP確認
- 公開後にGoogle Rich Results TestとSearch Console URL検査

## 実装順序

1. GitHub正本とGitHub Pagesの状態を確認して公開を復旧
2. SEO生成処理と自動テストを整備
3. トップページと信頼性情報を強化
4. 店舗、区、ガイドのメタデータ・本文・内部リンクを改善
5. 構造化データとsitemapを修正
6. build、静的HTTP、構造化データを検証
7. GitHub Pagesへ公開
8. Search Consoleでサイトマップと主要URLを確認
